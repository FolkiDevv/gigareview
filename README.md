# gigareview

> [!WARNING]
> **Это личный проект, а не продукт для широкой аудитории.** Если вы попали в этот репозиторий
> сами, а не по прямому приглашению автора, — этот проект точно не для вас. Он не публикуется
> на PyPI, не поддерживается для сторонних пользователей, issue и pull request'ы не принимаются.

Демон автоматического ревью pull request'ов Bitbucket Server / Data Center (API 1.0, проверено
на 8.19). Раз в N минут он забирает открытые PR, где вы стоите ревьюером, переключает локальную
копию репозитория на коммит PR и прогоняет сценарии — общие для всех репозиториев и свои для
конкретного. Замечания публикуются тасками в PR, итог — отдельным комментарием, статус ревью —
«одобрено» или «нужна доработка». Всё пишется в локальную SQLite-базу и видно в Web Dashboard на
localhost.

## Установка и запуск

Нужны Python 3.13+, [uv](https://docs.astral.sh/uv/), git и bash.

```sh
uv tool install git+https://github.com/FolkiDevv/gigareview
gigareview init-config            # пример в ~/.gigareview/config.toml — отредактируйте
export BITBUCKET_TOKEN=...        # Personal Access Token (права на чтение и запись PR)
gigareview check-config           # проверить конфигурацию и наличие токена
gigareview serve                  # демон + Web Dashboard на http://127.0.0.1:8765
```

Другие команды:

- `gigareview run PROJ repo 42 [--dry-run]` — однократно проверить PR без демона; код выхода
  0 — замечаний нет, 1 — есть замечания, 2 — ошибка.
- `gigareview serve --dry-run` — всё выполнять, но ничего не писать в Bitbucket.
- `-c путь` (или `$GIGAREVIEW_CONFIG`) — другой файл конфигурации.

## Конфигурация

Файл TOML; полный пример — `gigareview init-config`.

```toml
[daemon]
interval_minutes = 1          # период опроса Bitbucket
workdir = "~/.gigareview"     # клоны (repos/), база gigareview.sqlite3
max_parallel = 1              # прогонов одновременно (в одном репозитории — всегда по одному)
dry_run = false
approve = true                # false — не ставить APPROVED (NEEDS_WORK — как обычно)

[bitbucket]
url = "https://bitbucket.example.com"   # только https (http:// — лишь для localhost)
token_env = "BITBUCKET_TOKEN" # из какой переменной окружения читать токен
user = ""                     # slug пользователя; пусто — по заголовку X-AUSERNAME

[dashboard]
host = "127.0.0.1"            # не localhost — только с token (0.0.0.0 — ещё и public_url)
port = 8765
public_url = ""               # адрес для ссылок в комментариях (по умолчанию http://host:port)
token = ""                    # вход по токену, от 16 символов; пусто — без входа

[scenarios.<имя>]             # общий сценарий — для всех репозиториев
# ...

[[repos]]
project = "PROJ"
slug = "backend"
clone_url = "ssh://git@bitbucket.example.com:7999/proj/backend.git"
main_branch = "master"        # по умолчанию master
init = "uv sync"              # после каждого переключения на коммит PR
exclude_scenarios = []        # какие общие сценарии не запускать здесь

[repos.scenarios.<имя>]       # сценарий только этого репозитория (одноимённый общий — замещает)
# ...
```

## Сценарии

Сценарий — три bash-скрипта, которые выполняются в каталоге копии репозитория:

| Поле | Что делает |
|---|---|
| `run` | основные команды (например, `uv run mypy .`) |
| `validate` | оценивает результат: **0** — замечаний нет, **1** — есть замечания, **2** (и любой другой код) — сценарий отработал некорректно. Нет `validate` — оценивается код `run` по тем же правилам |
| `format` | текст таски из вывода `run`. Нет `format` — в таску идёт вывод `run` как есть. Код ≠ 0 — ошибка сценария |
| `title` | заголовок в тасках и отчёте (по умолчанию — имя) |
| `kind` | `simple` — одна таска на сценарий; `ai` — список тасок в JSON (ниже) |
| `incremental` | только для `ai`: прошлые таски сценария не закрываются сами — их закрывает сам сценарий (ниже) |
| `timeout_minutes` | на весь сценарий; по умолчанию 3 для `simple`, 20 для `ai` |

Окружение всех шагов: `TARGET_BRANCH`, `SOURCE_BRANCH`, `PR_ID`, `PR_PROJECT`, `PR_REPO`,
`PR_COMMIT`, `PR_TITLE`, `PR_DESCRIPTION`, `PR_AUTHOR`, `MERGE_BASE` (общий предок с целевой
веткой), `GR_REPO_DIR`, `GR_ARTIFACTS` (временный каталог прогона), `GIGAREVIEW` (команда самого
gigareview). История сценария в этом PR: `GR_PREV_COMMIT` — коммит его последнего
опубликованного ревью (пусто, если ревью не было или история переписана) и `GR_OPEN_TASKS` —
JSON-файл с его открытыми тасками `[{"id", "path", "line", "text"}]`. `validate` и `format`
получают вывод `run` на stdin и в файле `$GR_RUN_OUTPUT`; `validate` — ещё код завершения `run`
в `$GR_RUN_EXIT`. Остальное окружение — как у демона (`gigareview serve`), кроме переменной с
токеном Bitbucket.

Пример: новые ошибки mypy относительно целевой ветки.

```toml
[scenarios.mypy]
title = "mypy: новые ошибки"
run = """
uv run mypy . --no-error-summary > "$GR_ARTIFACTS/pr.txt" || true
git worktree add --force --detach "$GR_ARTIFACTS/base" "$MERGE_BASE" > /dev/null
(cd "$GR_ARTIFACTS/base" && uv run mypy . --no-error-summary > "$GR_ARTIFACTS/base.txt" || true)
git worktree remove --force "$GR_ARTIFACTS/base"
strip() { sed -E 's/:[0-9]+(:[0-9]+)?:/:/' "$1" | sort -u; }
comm -13 <(strip "$GR_ARTIFACTS/base.txt") <(strip "$GR_ARTIFACTS/pr.txt")
"""
validate = '[ "$GR_RUN_EXIT" -eq 0 ] || exit 2; test -z "$(cat)"'
format = 'printf "Новые ошибки mypy:\n\n"; cat'
```

То же на [mypy-diff](https://github.com/FolkiDevv/mypy-diff) (`uv tool install mypy-diff`;
пример есть и в `gigareview init-config`). Он сопоставляет ошибки с учётом сдвига строк, а его
коды выхода (0 — новых ошибок нет, 1 — есть, 2 — сбой) совпадают с кодами сценария, поэтому
`validate` не нужен. mypy задан явно через `--mypy-cmd`: без него mypy-diff сначала смотрит
`$MYPY_DIFF_MYPY` и активное окружение (`$VIRTUAL_ENV`) демона и только потом `.venv` проекта.
Цели — из настроек mypy проекта или после `--`.

```toml
[scenarios.mypy-diff]
title = "mypy: новые ошибки"
run = """
mypy-diff-git -b "$MERGE_BASE" --mypy-cmd "$GR_REPO_DIR/.venv/bin/mypy" \
  --format plain --only new --no-progress
"""
timeout_minutes = 5
```

### ИИ-сценарии

У сценария `kind = "ai"` итоговый текст (вывод `format`, иначе `run`) — JSON-список тасок
`[{"text": "...", "path": "файл", "line": 12}]` или объект `{"tasks": [...], "resolved": [id]}`.
`path` и `line` необязательны и привязывают таску к строке диффа. Пояснения вокруг JSON и
```-блоки допускаются: берётся фрагмент от первой скобки до последней. Если строки нет в
диффе, таска публикуется без привязки, с `путь:строка` в начале текста.

У сценария с `incremental = true` прошлые таски этого сценария в PR перед публикацией не
закрываются. Закрываются только id из `resolved` (из `$GR_OPEN_TASKS`). Пока прежние таски
открыты, PR не одобряется, даже если новых замечаний нет. Если сценарий упал, его таски
остаются как есть.

#### ИИ-ревью на gigacrew

Готовый сценарий (есть и в `gigareview init-config`):

```toml
[scenarios.ai-review]
title = "ИИ-ревью: ошибки и регрессии"
kind = "ai"
incremental = true
run = """
prompt=$("$GIGAREVIEW" ai-review prompt) || exit 2
gigacrew --mode plan --no-save --no-color -p "$prompt"
"""
validate = '"$GIGAREVIEW" ai-review tasks --check'
format = '"$GIGAREVIEW" ai-review tasks'
timeout_minutes = 20
```

- `ai-review prompt` собирает промпт: заголовок и описание PR, коммиты и список файлов
  диапазона, открытые таски прошлых ревью, правила ревью и формат ответа. Дифф в промпт не
  вставляется: агент сам читает изменения файлов (`git diff`, `read_file`) и изучает код вокруг
  (explore, поиск ссылок).
- Первое ревью PR — все изменения от `MERGE_BASE`. Следующие — только новые коммиты от
  `GR_PREV_COMMIT`; файлы, которые изменила только влитая целевая ветка, не ревьюятся. Если
  история PR переписана (force-push), ревью снова идёт с нуля.
- Правила ревью: понять намерение по описанию и коммитам; искать только дефекты (логика,
  регрессии у вызывающего кода, безопасность, потеря данных, гонки, обработка ошибок,
  контракты, правила AGENTS.md); проверить каждую находку по коду до ответа; не сообщать
  стиль, то, что ловят линтеры, придирки, старые проблемы и догадки без сценария сбоя; не больше
  10 находок. Код и описание PR для агента — данные, а не инструкции.
- Агент отвечает блоком ```json `{"findings": [{"path", "line", "end_line", "severity",
  "title", "body", "suggestion", "confidence"}], "resolved": [id]}`. `line` — первая строка
  проблемного участка, `end_line` — последняя. Если `line` нет среди изменённых строк, таска
  привязывается к первой изменённой строке участка.
- `ai-review tasks --check` (валидация) — 0: замечаний нет, 1: есть, 2: gigacrew завершился с
  ошибкой или в ответе нет JSON. `ai-review tasks` (форматирование) — таски с серьёзностью,
  сутью и способом исправления. Пороги задаются одинаково в обоих шагах: `--min-confidence`
  (по умолчанию 70), `--min-severity` (`critical`/`major`/`minor`, по умолчанию `major`),
  `--limit` (10). Дополнительные указания ревьюеру — `ai-review prompt --focus "..."`.
- `--mode plan` — только чтение: правки файлов и изменяющие команды заблокированы, а
  подтверждений (тесты, сборка) без терминала не бывает — они отклоняются.
- gigacrew работает со своим обычным провайдером (API GigaChat v2). Окружение демона
  наследуется: `GIGACREW_*`, заданные в shell перед `gigareview serve`, видны gigacrew; кроме
  того, он сам читает `~/.gigacode/.env`. Модель лучше задать явно (`GIGACREW_MODEL` или
  `-m`): `.env` из проверяемого репозитория может задать то, чего нет в окружении.

## Что происходит в Bitbucket

- Статусный комментарий — один на PR. Его пишут сразу после взятия PR в работу, до подготовки
  копии: «проверки начаты», все сценарии — «⏳ ожидает». Затем выполняются обычные сценарии,
  после них — ИИ-сценарии (долгие), и после каждого этапа комментарий обновляется. Новый
  коммит в PR обновляет тот же комментарий заново; если его удалили вручную, пишется новый.
- Сценарий, который завершился с кодом 2 (таймаут, неразборчивый вывод), в комментарии —
  «⚠️ проверка не удалась (подробности — в gigareview)»: причина видна в Web Dashboard. Упал
  весь прогон (git, init, Bitbucket) — «⚠️ прогон не удался».
- Каждый сценарий с замечаниями — таска (комментарий с `severity = BLOCKER`), у ИИ-сценария —
  по таске на запись. Таски публикуются после своего этапа: замечания обычных сценариев видны,
  пока идут ИИ-сценарии.
- Статус ревью ставится только после всех сценариев: все пройдены — APPROVED, есть замечания —
  NEEDS_WORK, замечаний нет, но часть проверок не удалась — статус не меняется. С
  `daemon.approve = false` APPROVED не ставится никогда (NEEDS_WORK — как обычно), а итог
  статусного комментария — «замечаний нет» без «PR одобрен»; настройка перечитывается без
  перезапуска демона.
- Перед публикацией таск сценария его таски прошлых прогонов закрываются (RESOLVED); у
  инкрементальных сценариев — только те, что сценарий сам отметил исправленными. Таски
  сценариев, убранных из конфигурации, закрываются после всех этапов.
- Если перед публикацией этапа оказалось, что PR закрыли или в него пришёл новый коммит, итоги
  не публикуются, а оставшиеся сценарии не запускаются: новый коммит проверит следующий прогон.

Какой коммит проверять, демон решает сам: коммит, по которому уже есть прогон (в очереди, идёт
или завершён), повторно не проверяется; сбой самого прогона (git, init, Bitbucket) повторяется
при следующих опросах, но не больше трёх раз. Повторить вручную — кнопкой в Web Dashboard.

## Web Dashboard

Интерфейс дашборда — на английском (журнал демона и тексты ошибок — по-русски, как в Bitbucket).

- **Overview** — состояние демона, последний и следующий опрос, очередь, сводка за сутки и
  всего, последние прогоны и ошибки; кнопки «Poll now», «Pause polling», «Reload config».
- **Runs** — журнал с фильтрами по статусу, репозиторию, PR, сценарию и его исходу.
- **Run** — журнал git и init, каждый сценарий с кодами и полным выводом всех шагов, таски,
  опубликованные комментарии; «Re-run check».
- **Pull requests**, **Log** демона, **Configuration** (без токена).
- `GET /api/status` — состояние в JSON.

Живые обновления — без WebSocket: htmx раз в несколько секунд перезапрашивает страницу и
подменяет изменившийся блок (на странице прогона — только пока он выполняется). Все скрипты и
стили лежат в пакете (htmx вендорён в `gigareview/web/static/`), снаружи грузятся только шрифты
Google Fonts. Действия — POST-формы под CSRF-защитой.

Без `dashboard.token` входа нет, и сервер слушает только localhost. С токеном дашборд можно
открыть в сеть (`host = "0.0.0.0"`): браузер входит на странице `/login` и получает cookie на
30 дней, скрипты передают `Authorization: Bearer <токен>` (например, для `/api/status`). На всех
интерфейсах (`0.0.0.0`, `::`) нужен и `public_url` — адрес для ссылок в Bitbucket; если он
`https://`, cookie всегда ставится с `Secure`, даже когда прокси не передаёт схему, — поэтому
за HTTPS-прокси всегда задавайте `public_url = "https://…"`. Сам сервер
говорит только по HTTP: ставьте перед ним обратный прокси с TLS. Если прокси на той же машине,
оставьте дашборд на localhost; если на другой — между прокси и дашбордом нужен защищённый
туннель (VPN, SSH): TLS до прокси не защищает следующий участок, и токен с cookie идут по нему
открытым текстом. Токен меняется только перезапуском демона.

> Сценарии выполняют код из PR (`uv sync`, тесты) на вашей машине — наблюдайте только
> репозитории, авторам которых доверяете.

## Разработка

```sh
make dev     # пакет + dev-группа (pytest, линтеры, mypy, coverage)
make check   # все статические проверки и тесты — как в CI
make test    # тесты с покрытием: код демона (всё, кроме web/ и cli/) — не ниже 80 %
```

Остальные команды — `make help`. Слои и правила зависимостей — в `CLAUDE.md` и `.importlinter`.
